# B1 — Order integrity and financial exception audit

Backend only. No production mutation, merge or deployment is authorized from this development PR. Base main `bc3f560cf296cc03eeb93d0f917cca4256951d38`. Shared early handoff: `docs/backend-p0-v1.md` on `codex/notification-delivery-b3`.

## API

Admin Bearer session required. `GET /api/admin/order-management/:reference` returns `{success,order,eligibility:{archive,restore,deleteTest,denials},history}`. `order.archived_at` is nullable and its status is the original database status. `POST` on the same path accepts exactly `{action:'archive'|'restore'|'delete_test',confirmed:true,reason,expectedUpdatedAt,requestId}`. Reason is 5–500 safe characters; request ID 8–64 `[a-zA-Z0-9_-]`. Result `{success,action,orderId,archivedAt,deleted}`. 400 validation; 401/403 auth; 404 missing order; 409 changed row, reused request or eligibility; 503 unavailable durable storage. No memory fallback for staff archival/deletion. All responses are non-cacheable. Fetch current details before confirmation. A replay of the same successful request returns its stored result even after the fixture is gone. Changed request payload or actor is rejected.

Existing Admin order listing gains `archived=exclude|only|include`, default exclude. Archive does not erase an order, change payment/fulfilment state, mark a case resolved, remove financial reporting or remove paid customer-owned history. Active, uncertain, unresolved paid and unverified-refund cases cannot be archived. Stale pending attempts need at least 24 hours before archival. Restore reverses archival only.

Deletion requires trusted `order_test_fixtures` provenance registered by an isolated test harness, no account, no payment/supplier/referral/commercial/managed-store/resolution evidence and a closed unpaid attempt. No Admin API creates provenance or marks real orders as tests. A prefix such as MH-TEST is insufficient. Existing real/unproven rows remain ineligible and may be archived instead. Deletion refuses any incoming foreign-key evidence, including CASCADE/SET NULL relationships and future tables; finance JSON/order references are also checked. It locks the order and serializes relevant financial writes. Exactly one order must be affected. Provenance removal, deletion, append-only decision history and existing Admin audit commit together or fully roll back. No existing unrestricted delete helper is exposed. Denial codes: TEST_PROVENANCE_REQUIRED, CUSTOMER_LINKED, PAYMENT_EVIDENCE, NOT_CLOSED, SUPPLIER_EVIDENCE, CONNECTED_EVIDENCE, UNSETTLED.

## Historical unpaid attempt

Read-only production inspection confirmed `MH-20261001-858321` is stored failed/payment pending, with no paid/submitted/delivered timestamp or supplier order ID. It carries a 400-minor-unit estimated supplier cost, which is not dispatch evidence. No stored facts were changed.

The reusable predicate identifies failed, unpaid Paystack attempts with no payment, dispatch, delivery, manual-review, resolution or store evidence. They are excluded from customer-owned routine order lists and customer order counts, not financial evidence. Public tracking of such an attempt older than 24 hours projects `status:'expired',classification:'unpaid_attempt'`; ordinary orders project `classification:'order'`. Admin responses preserve raw `status:'failed'` while exposing the classification. Payment history is neither rewritten nor fabricated. Current successful, dispatched, uncertain and externally assisted orders never qualify for this projection.

## Store Earnings audit — founder decision, no money moved

Read-only production aggregate inspection on 25 October 2026 found nine available `store_sale` operations totalling **582 pesewas / GH₵5.82**, matched by nine Store ledger entries with the same net balance. No Store withdrawal operations appeared in that aggregate. The current stored withdrawal minimum is 500 pesewas / GH₵5.00 and fee is 300 basis points / 3%. Available figures are account aggregates, not a claim that every website individually owns that balance.

`FinanceTx.storeEarnings()` computes available from the immutable Store ledger; pending from pending sales; reserved includes both pending_review and approved-but-unpaid withdrawals; withdrawn includes paid withdrawals. Website deletion deliberately refuses remaining earnings so access to funds is not stranded. No archived website with linked financial history was found in the checked aggregate.

The owner-level aggregate confirms **three owners with nonzero balances, ranging from 71 to 302 pesewas (GH₵0.71–GH₵3.02)**. Every balance is below the 500-pesewa minimum. The global GH₵5.82 cannot be treated as one owner's withdrawable balance. This reproduces the residual-balance deletion blocker: the ordinary withdrawal workflow cannot clear these owners' small balances.

The existing owner-authorized Store Earnings withdrawal workflow remains the normal supported settlement path, with server amount/fee checks, reservation, Admin review, externally completed payout evidence and immutable ledger. This PR does not submit a withdrawal or mark one paid. A below-minimum waiver, alternative compensation, write-off or administrative balance conversion would create money-moving policy and **requires separate founder approval**. Settlement is therefore explicitly not implemented. No balances, fees, minimums or financial records are changed here.
