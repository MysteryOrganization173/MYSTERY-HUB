## Actual formula
server/services/referralEconomics.ts is the calculation engine. With disabled/no economics policy, Data fixed rewards are capped to max(0, customer amount - order supplier_cost_minor - quoted processing reserve), not scaled upwards with larger profit. Unknown supplier cost pays zero. Legacy orders without a quoted reserve and disabled policy calculate with zero reserve; this is a historical compatibility behavior, NOT proof that payment processing is free. New direct snapshots explicitly preserve known or unknown reserve.

An enabled margin_percent policy computes min(margin, percentMinor(margin, marginBps)); the selected rule still gates eligibility. No universal live percentage is inferred from source. The stage_margin_percent branch supports acquisitionBps and recurringBps. shared/dataReferralPolicy.ts recommends exactly 5000/2000 bps (50%/20%), but does not activate anything. These percentages apply only when a saved enabled stage policy supplies them. It calculates first qualifying direct Data reward as round-half-up(50% * max(0, normal undiscounted retail - actual supplier order cost - normal processing reserve)). A recurring direct Data reward is round-half-up(20% * max(0, actual paid retail - actual supplier order cost - actual processing reserve)). Larger verified margin produces larger rewards. There is no fixed 50/10 cap in stage mode. Missing cost or reserve yields zero. Negative margin clips to zero, not a recurring subsidy. AFA needs an independently enabled explicit AFA rule/policy; other services do not inherit Data stage percentages. Managed reseller orders are excluded before reward processing.

The old fixed engine's Welcome acquisition exception pays the selected full fixed/percentage-of-payment rule when a server-persisted welcome-v1 snapshot is valid, the buyer has a canonical account phone and this is acquisition. It can knowingly produce negative contribution. Unknown supplier cost still fails closed. The dynamic branch uses normal contribution for the first reward; Welcome reduces actual retained contribution without reducing the normal reward basis. Contribution remains customer payment - actual supplier cost - actual processing reserve - actual referral reward. This loss is explicitly recorded as acquisition subsidy. Recurring orders receive no one-time Welcome Offer and use ordinary actual economics. An unknown reserve prevents a trustworthy retained-profit estimate.

## Authority, rounding and precedence
Costs come from the immutable order supplier_cost_minor captured from the authoritative supplier resolution, never a guessed retail percentage. Only AFA has an explicit admin flat-cost fallback. New commercial_context reserveMinor/normalReserveMinor snapshots win. When these are absent, an explicitly configured direct-pricing reserve wins over economics:data reserve; the latter must be reserveConfigured for stage mode. Percentage reserves are applied separately to actual and normal revenue. shared/money.ts uses integer BigInt round-half-up, so one pesewa of margin at 50% rounds to one pesewa. Stage configuration validates both percentages in 0..10000; no additional automatic reward cap/minimum is implemented beyond zero margin and positive integer reward admission. Approval includes the existing ordinary reward eligibility checks.

## Complete attribution and funds path
src/context/AppContext.tsx and src/utils/referralCapture.ts capture URL code, persistent visitor key and capture ID -> /api/referrals capture -> ReferralService.captureVisitorReferral and ReferralStore.recordClick/bindAttributionToUser. Signup binds the first valid lifetime attribution. Self/circular referrals and mismatched attribution are rejected. Orders persist attribution/referrer and quoted commercial context. ReferralService.processOrderReward requires delivered + payment_status success + GHS, re-reads the order inside the relationship/order transaction, checks referrer status/rewardAllowed and canonical identity, and selects acquisition versus recurring using previous rewarded/qualifying orders. Rules prefer product, network, service and specific stage, then newest created_at/id tie-break. Only level-one rewards are automatically created; stored level-two/three values remain dormant. Anonymous identity may select any/standard rules rather than acquisition, so do not equate all visits with first qualifying customers.

The unique ledger/order/idempotency controls stop duplicate callback/webhook rewards. Automatic eligible delivered rewards are created approved, not a compulsory pending waiting phase. Existing pending/rejected/reversed records keep their status semantics. metadata_json stores paid/normal retail, cost/source, reserve, rewardable margin, actual percentage, mode/version, selected rule, final reward, subsidy and retained contribution. Existing original ledger entries are returned before recomputation, even if reversed. Configuration changes do not back-pay, recalculate or replace history.

FinanceService computes available earnings from approved referral ledger less transfers/withdrawal reservations/reversals, not gross referred revenue. Earnings-to-Wallet transfer is authenticated, owned, restricted-account checked, serialized and idempotent; Wallet transfer is irreversible. Withdrawal minimum/fees/settings and settlement/reconciliation remain separate. Definitive refunds reverse the recorded original amount once. Spent/reserved rewards enter restriction/manual reconciliation rather than silently creating a negative balance. Temporary failure/queued/refund_pending is not authority to reverse. Inspect referral ledger snapshots, relationship stage, cost/reserve and financial operations to explain customer GH₵40 referred revenue vs GH₵0.80 reward. Revenue alone cannot prove underpayment, and this audit did not inspect a real customer account.

## Synthetic evidence
scripts/auditDataReferralEconomics.ts calls the actual pure engine without any database reads or configuration writes. docs/data-referral-economics-synthetic-v1.csv contains 16 scenarios for catalog MTN 1GB, AT 1GB, MTN 10GB and MTN 40GB, using explicitly synthetic costs, GH₵0/GH₵1 Welcome and configured 0/10-pesewa reserves. It compares fixed first/repeat and dynamic first/repeat, normal/actual margin and retained contribution. These are calculation examples, not live supplier quotes. AT 1GB with synthetic 390-pesewa cost, 10-pesewa reserve and GH₵1 Welcome demonstrates an intentional negative acquisition contribution. Unknown cost, unknown reserve and negative recurring margin fail closed. Repeat comparisons use regular retail and no Welcome discount. Real activation needs current supplier cost evidence.

## Public truth and activation gate
GET /api/referrals/rules exposes enabled rule fields, not the effective saved economic policy. EarnRules and describeReferralReward therefore describe the selected fixed rule (50/10 when enabled) even if a separate margin policy supersedes it. The existing customer footnote warns that Data may use a separate margin policy and recorded activity confirms the actual amount, but it cannot describe effective 50%/20% accurately. Do NOT advertise or enable dynamic rewards until the public effective-policy contract/copy is separately reviewed. This sprint leaves public amounts and finance logic unchanged.

Before founder activation: obtain current authenticated rule/economics/direct-reserve config, verify actual supplier order costs and reserve source, approve 50%/20% normal/actual basis and acquisition loss budget, review unknown-cost behavior/legacy compatibility, verify effective policy in public copy, and validate immutable snapshots/admin warnings with disposable fixtures. Only then explicitly save an operator-approved policy. No migration, historical repair, bulk relabeling, automatic activation or live transaction is needed in this sprint. Backend Commercial Pricing repair also requires separate approval.
