# Installed-app notification onboarding correction

The old launch card requested browser permission only. Granting permission did not create a server-bound device, and the card did not offer the separate optional marketing choice. This correction uses the existing reviewed HTTP client and push-registration helper; no backend routes, schema, economics or delivery worker changes.

On signed-in installed Home, outside checkout/auth/editor/account overlays, read enabled configuration and current device state after the existing short delay. On an explicit Enable notifications tap: validate configuration, request native permission if it is still default, subscribe/bind to the actual current session, and require server confirmation. Then immediately offer customers **Want offers, discounts and news too?** with **Yes, send me offers** and **Not now**. Only affirmative acceptance writes marketing=true, preserving the latest transactional preference. A failed save stays retryable, never pretends consent succeeded.

Previously granted but unregistered devices receive a one-tap completion card. Already registered customers with an unanswered offers choice can see that choice directly. Declined/unsupported/disabled cases do not trigger permission prompts. A remembered answer is scoped to the account on this device and is not an authorization/consent source. My Account remains available for changing choices. Staff are not presented with a customer-marketing enrollment prompt; existing backend customer-only audience eligibility stays unchanged.

Account/session keys, abort checks around async setup/preferences and synchronous in-flight locks prevent stale responses and duplicate taps from enrolling a different account. Public customer websites and iframe previews stay excluded. The push-only worker and generic, authenticated notification-click behavior are unchanged. Browser permission, registration, provider acceptance and observed receipt remain distinct.

Release keeps production settings.paused=true and the three marketing templates disabled. This UX correction does not resume sending or queue a campaign. The founder's existing registered device is attached to an admin account; the existing single-customer marketing-test API will not target it. Do not weaken that restriction or fake an order/payment to manufacture a test. Controlled customer-device receipt/click-through acceptance remains a separate pending gate.
