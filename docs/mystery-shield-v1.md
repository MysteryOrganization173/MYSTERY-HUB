# Mystery Shield V1 evidence and release plan

Current main reviewed at 1bfff4ea9f494a38a2eecf551872cbc5624e2488, including the checkout recovery, financial reconciliation, Campaign Manager, Builder and Mystery AI releases. The held supplier contract PR #69 stays outside this work.

- Payments use the existing Paystack reference/amount/currency validation, signed webhook handling and atomic paid-order update. Wallet purchases commit the debit and successful order together. Shield reads the recorded paid_at and status. It neither verifies a payment independently nor mutates the original order.
- The authoritative catalog labels the direct MTN product IDs Express. The supplier resolver can select a sole MTN offer without requiring an Express slug. Require an exact separately approved persisted offer reference as well as an exact product ID.
- Supplier status refresh can record a check timestamp even when a lookup fails. The generic supplier mapper also converts unknown states to processing. Shield requires a fresh successful GET with explicit matching supplier identity and documented pending/processing status. A missing identifier, inconsistent timestamps or unresolved support evidence prevents eligibility.
- Public order lookup is reference-based with masked details. The reference alone cannot authorize a reward. Shield uses the existing authenticated user_id ownership and preserves guest tracking. Guests need a separately designed verified recovery path.
- The existing Instant Bundles API exposes fixed/flexi catalog, POST placement and GET by supplier identifier. Neither source nor existing contract evidence establishes an exact 400MB product, current cost, beneficiary policy, outage independence, or safe replay by client reference. The previous GH₵2.94 figure is illustrative. Live adapter and notifications remain held.
- Existing Web Push uses transactional preferences, active session/device bindings, durable deduplication and generic lock-screen copy. A later Shield scheduler must use this infrastructure and recheck current eligibility before enqueue/send. Manual tracking uses no notification permission.
- Separate private schema will be a manually applied SQL file, with no startup integration. Application release and migration approval are separate. Production composition has no reward adapter or scheduler, even if environment flags are changed. Use only disposable database and synthetic supplier evidence in tests.

## Release and activation decisions

The public Instant Bundles catalogue was available on 5 November 2026 and returned 61 products. Its single exact 400MB entry was fixed package 9 for AirtelTigo. This proves the visible catalogue contains no matching MTN 400MB entry at that observation. It does not establish the complete supplier assignment, current wholesale cost or an MTN equivalent. [Public catalogue](https://mysterybundlehub.com/api/instant-bundles)

The status parser uses the supplier contract snapshot's success envelope and matches public ID, beneficiary, MTN network and original size. The current order is reread after a quote and locked at reservation. Both current supplier evidence and local eligibility are required. V1 accepts verified Paystack or atomically paid Wallet orders. Delivered orders are excluded even if delivery came after nine hours. The programme start excludes orders created before launch. Only current submitted/processing orders with valid pending/processing supplier evidence qualify.

The application ships without a registered Shield gateway. Configuration switches for visibility, claim intake, fulfillment and notifications default off. Changing flags alone cannot enable dispatch. The admin panel reports the requested settings separately from actual readiness. The protected status route supplies no reward access to reference-only guests. A missing optional schema fails closed. The SQL file installs two private tables and starts paused. It is deliberately absent from startup, GitHub deployment and the standard schema mirror. Review and approve a manual installation separately.

The durable claim ID and original order uniqueness survive retries and restarts. A locked singleton serializes budget reservations by Ghana calendar day and across the full programme history. The reservation commits a one-time submission latch before invoking the test gateway. A lost reply stays held, with no customer retry or automatic repeat POST. The synthetic recovery path requires the recorded supplier ID and explicit delivery evidence. A confirmed supplier rejection retains reserved budget in V1 until a future approved reconciliation policy can release it. Staff diagnostics separate reserved liability from verified reward cost and show up to 50 recent claims. The audit trail retains reservation, dispatch, acceptance and resolution timestamps, plus the staff pause event. A live count of eligible orders would require a bounded evidence scan, so this release does not report an estimate.

Activation requires a separately approved production schema installation, exact supplier-side fixed MTN 400MB availability, verified price and beneficiary restrictions, an enforceable supplier charge ceiling, status/reconciliation contract verification, budget and dates, and founder approval of coverage and wording. The existing Instant Bundles POST contract does not expose a maximum-charge field. A local cap alone cannot guarantee the provider will honor the quote. With the separate approval and production adapter in place, a staff member can pause new reservations from Orders & delivery. A pause cannot recall a request already latched for dispatch. Emergency operational shutdown must also disable intake and fulfillment through the approved deployment controls.

Existing Web Push is available for transactional account notifications. A Shield-specific bounded scheduler and an eligibility check at enqueue/send are still required. No Shield push template, event, timer, permission request or dispatch was enabled. The manual claim flow requires no push subscription. No physical Android or device-level push tests were conducted.
