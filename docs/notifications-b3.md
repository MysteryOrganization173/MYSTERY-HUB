## Configuration and release gates

All these variables belong on the backend. No production settings were changed here:

- `WEB_PUSH_ENABLED`: literal `true` enables sending only when every required key validates and PostgreSQL is available. Absent/false leaves subscription creation and campaign sends unavailable and the worker stopped.
- `WEB_PUSH_VAPID_PUBLIC_KEY`: public base64url uncompressed P-256 public key. The public config endpoint may expose this key only.
- `WEB_PUSH_VAPID_PRIVATE_KEY`: secret base64url P-256 private key matching the public key. Generate a pair with the pinned `web-push` library in a secure operator workflow; never commit it.
- `WEB_PUSH_VAPID_SUBJECT`: non-secret operator contact, e.g. `mailto:support@mysterybundlehub.com` if that mailbox is actually monitored, or a valid operator HTTPS contact URL.
- `WEB_PUSH_STORAGE_KEY`: secret base64 encoding of **32 random bytes**, used for AES-256-GCM subscription encryption. Preserve securely with backups. Changing it without an explicit re-encryption/re-subscription procedure makes existing devices unreadable. Do not rotate blindly.

Existing `DATABASE_URL` remains authoritative and unchanged. Existing backend `GEMINI_API_KEY` is optional for draft assistance only. Push does not require Gemini or another hosted queue. No new model was invented: drafting reuses the existing documented `gemini-3.1-flash-lite` model. Account-specific access is unverified here.

Release requires: review additive schema/role permissions on the deployment role, verify a recoverable backup, deploy backend with delivery disabled, integrate Claude's consent/preferences/device/inbox UI, verify `/push-sw.js` at the actual production origin as JavaScript, then configure keys and test with an explicitly consenting founder device. Verify both actual Render revisions and the app's production origin; do not infer success from a preview host. No provider or native-device delivery was performed in this development task. Until that controlled acceptance passes, report real delivery **UNVERIFIED**, not working.

## Authentication and common errors

Existing live Bearer-session middleware remains authoritative, including account status and forced password change. Customer endpoints require that session; Admin endpoints require the existing Admin role. Every response is `Cache-Control: no-store`. No caller supplies its own account identity for a subscription. Unknown body fields are rejected on mutations. Errors use `{error:string}`; 400 invalid input, 401 missing/invalid session, 403 role/password-change restriction, 404 non-owned/missing resource, 409 changed state/confirmation/audience, 429 throttle, 503 disabled/unavailable storage or provider. Never display an error as send success.

## Customer contracts

All paths below start `/api/notifications`:

- Public `GET /config` -> `{enabled:boolean,publicKey:string|null,workerPath:'/push-sw.js'}`. Treat `enabled:false` as unavailable, not subscribed or delivering.
- `GET /preferences`, `PUT /preferences` with exactly `{transactional:boolean,marketing:boolean}` -> the same two booleans. Defaults: transactional true, marketing **false**. Browser permission and these account preferences are separate.
- `PUT /subscriptions` with `{subscription:{endpoint,expirationTime?:number|null,keys:{p256dh,auth}}}` -> `{success:true,deviceId}`. Only valid HTTPS endpoints for FCM, Mozilla, Apple and Windows Push are accepted; IPs, localhost, credentials, unsupported hosts/ports and malformed curve keys fail closed. Up to ten devices per account. A different account cannot take an endpoint with different encryption keys. Binding is to the current database session, not merely an account ID.
- `GET /subscriptions` -> `{success:true,devices:[{id,created_at,updated_at,current_session}]}`. No subscription URL or key is returned.
- `DELETE /subscriptions/:id` -> `{success:true}`; only the current user's device can be removed. UUID required; deletion is deliberately idempotent.
- `GET /inbox?offset=0` -> `{success:true,items:[{id,createdAt,title,body,destination}]}`. Page size 25; offset integer 0–100000. This is authenticated event history, **not proof of device display or reading**.
- `GET /inbox/:id` -> `{success:true,notification:{id,createdAt,title,body,destination}}`. Missing or another account's ID returns 404. Only `/orders` and `/app` destinations are generated by the server; no arbitrary URLs or order credentials are embedded.

Reusable models are in `shared/notifications.ts`; these examples document the response envelopes and snake-case fields where applicable. Do not infer browser permission from device persistence. UI states should distinguish unsupported, permission default/denied/granted, disabled configuration, registered device, revoked/expired session and transient failure.

## Admin contracts

All paths below start `/api/admin/notifications` and require Admin authorization:

- `GET /templates` -> `{success:true,templates:[{id,title,body,category,enabled,locked,version,updated_at}]}`.
- `POST /templates` with `{id,title,body,category:'marketing',enabled}`; `PUT /templates/:id` with `{title,body,category:'marketing',enabled,expectedVersion}` -> saved template row. ID: 3–64 lowercase safe characters, starting with a letter. Title 3–80, body 5–240. Expected version is mandatory for edits. Built-in transactional templates are locked; do not offer edit controls for them. Custom transactional claims are prohibited.
- `GET /templates/:id/history` -> `{success:true,history:[{version,snapshot,actor_id,created_at}]}`, at most 50 versions. Writes and pause/campaign actions also use the existing Admin audit store.
- `POST /preview` with `{templateId}` -> `{template,preview:{title,body}}`; safe synthetic sample, no customer lookup. Allowed placeholders are exactly `{{appName}}` and `{{eventLabel}}`. Unresolved variables and unverified promotional amounts, discounts, URLs, credential fields or payment/delivery claims fail validation.
- `POST /audiences/preview` with `{templateId,userId?}` -> `{success:true,previewId,eligibleDevices,eligibleCustomers,expiresInSeconds:600,enabled}`. Only enabled marketing templates; only active, subscribed customers with explicit marketing opt-in and valid sessions. Optional `userId` selects one customer, not a permission bypass. Maximum 1000 devices per prepared campaign. Counts are not exposed publicly.
- `POST /campaigns` with `{previewId,requestId,confirmed:true}` -> `{success:true,campaignId,eligibleDevices,duplicate:boolean}`. Request ID: 8–64 alphanumeric/underscore/hyphen. Preview is actor-bound, expires, and can create only one campaign. An identical request replays its original result; changed/reused request conflicts. Template version and eligible device set are checked again; changes require a fresh preview. Zero audience, pause or missing configuration prevents sending. The actual worker rechecks account/session/preferences again.
- `GET /campaigns?offset=0` -> `{success:true,campaigns:[{id,actor_id,preview_id,recipient_count,created_at}]}`, 50/page.
- `GET /deliveries?offset=0` -> `{success:true,deliveries:[{id,event_id,user_id,state,attempts,last_code,created_at,updated_at,history:[{attempt,code,started_at,finished_at}]}]}`, 50/page. No endpoint/private key/provider body appears. States: `queued`, `retry`, `provider_accepted`, `invalid`, `failed`, `skipped`. `provider_accepted` never means displayed, read or acknowledged. An unfinished `started` attempt can represent a crashed/expired lease.
- `GET /health` -> `{configuration:{enabled,valid},deliverySemantics,devices,pending,failed,paused}`. This is local configuration/queue health, not a live provider probe.
- `GET /settings` -> `{paused}`. `PUT /settings` with `{paused:boolean,confirmed:true,reason}` -> `{paused}`. Safe reason 5–200 characters; auditable. This changes operational pause only, not secrets or browser consent.
- `POST /draft` with `{mode,templateId}` -> `{success:true,draft:{title,body},source:'gemini',basedOn:'server-approved generic template',requiresReview:true,sent:false}`. Modes: shorten, clarify, grammar, professional, friendly, titles, variation. Only the eight built-in IDs are accepted. Gemini sees canonical generic text, **never edited/custom text, customer records or recipient lists**. Five-second cancellation/deadline; output/placeholder/claim validation. Six requests/minute per Admin. No draft saves a template, chooses recipients or sends a notification. Locked transactional content remains server-owned even after producing a draft.

Eight defaults: payment_confirmed, order_processing, order_delivered, delivery_attention, refund_update; maintenance, new_service, special_offer. The latter three are opted-in marketing only. Arbitrary discounts and unsupported fulfilment statements are deliberately not expressible in custom campaigns in this release.

## Durable events and financial isolation

The additive runtime SQL and `schema.sql` mirror create private schema `mysteryhub_notifications` with preferences, devices, templates, versions, events, deliveries, attempts, audiences, campaigns and pause settings. All tables use RLS; schema/table access is revoked from PUBLIC, anon and authenticated. Functions are invoker-context, not SECURITY DEFINER. The trusted backend migration role owns/operates the private schema. A distinct non-owner runtime role requires explicitly reviewed least-privilege grants/RLS policies before rollout; do not expose these tables through public Supabase APIs.

An order trigger commits an immutable template snapshot/outbox event in the **same transaction** as authoritative order facts. It uses the existing final stored states reached by verified-payment, Success Biz Hub webhook and reconciliation paths; it does not call or replay those operations. Events require an authenticated order owner, Paystack/Wallet success and `paid_at`. Processing also requires accepted supplier ID/submission timestamp; delivery requires delivery timestamp and supplier ID or completed Marketplace fulfilment. Payment alone never means delivery. Uncertainty yields a neutral attention message. Refund completion notifications require verified resolution evidence; raw `refunded` status is insufficient. No historical backfill occurs on migration. No user or financial rows are rewritten.

Event keys and per-device uniqueness deduplicate repeated webhooks/reconciliation. Rollback removes the event along with the order transition. Outbox persistence intentionally remains atomic: a database/schema permission failure must not silently lose an event; therefore verify migration/role compatibility before release. Provider network/timeout/retry failures occur after commit and cannot change payment, order, supplier or ledger state. No provider request occurs inside a financial database transaction.

Workers claim one short-leased job at a time with PostgreSQL `FOR UPDATE SKIP LOCKED`; separate processes/connections cooperate. Restarted/expired leases recover. Up to five transient attempts, exponential delay capped at 30 minutes; permanent provider errors stop, 404/410 revokes only the matching device binding. Queue is serviced every ten seconds in the existing backend process, not an additional Render worker. Events older than 24 hours are not sent. No attempt claims exactly-once network delivery: a crash after provider acceptance but before local recording can retry. Stable notification tags collapse duplicates where supported. No duplicate financial operation is possible because workers have no financial/supplier execution path.

## Service worker and frontend responsibilities

`public/push-sw.js` is push-only: no fetch interception, offline cache, account token or transcript storage. It ignores supplied text/destination and shows a generic Mystery Hub update with an opaque event UUID. A late in-flight packet after logout/account switch cannot reveal order text, phone, name or amount. A click opens `/orders?notification=<uuid>` at the same origin, avoiding customer `/sites/` windows. **Claude must resolve that UUID through the authenticated inbox endpoint before showing details or following its destination**, including after sign-in. A different account gets 404. Do not put private data in URLs or assume an existing browser session owns a notification.

Frontend should register this worker on the app's origin/scope only after an explicit consent flow, request permission on a user gesture, subscribe with the returned public VAPID key, then bind the subscription with the current Bearer session. Do not subscribe customer-generated websites or automatically ask for permission. Re-register/rebind on account/session changes. Logout removes database sessions and cascades device revocation; send `CLEAR_ACCOUNT_NOTIFICATIONS` to close existing generic notices, and unsubscribe locally when appropriate. Never persist tokens in the worker. Browser subscription rotation must rebind from an authenticated page; no unauthenticated pushsubscriptionchange handler guesses an account. Existing PWA manifest/installation identity is unchanged.
