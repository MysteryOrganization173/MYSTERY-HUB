# SMS provider validation incident diagnostics

After P0 activation, three genuine automatic submissions received HTTP422 VALIDATION, without provider message IDs or an observed credit decrement. No failed/uncertain submission is retried by this change. Configuration-presence and credit checks alone cannot prove sender approval or successful SMS submission.

The existing backend client now reads the documented GET /api/v3/sender-ids/{senderId}/status at most every10minutes while the SMS worker is configured and storage is installed. It never registers a sender, rotates secrets or submits a test message. Stored private metadata contains only sender, documented status enum, documented positive documentation-required classification, config identity and timestamps. Provider organization names, comments, prose, credentials and customer information are not persisted.404 remains unverified because the provider documents shared-sender ambiguity.

A confirmed pending/rejected/blocked sender or documented required-documents response blocks before claim/network markers and records a persistent incident pause. The transaction locks the CURRENT settings row, preserves its policy/cutoff and external operator changes, increments the actual revision, disables automatic policy/pauses SMS, appends an audit with the real database role, and cancels only queued messages that never acquired a network marker. Every failed, uncertain, attempted or provider-ID record remains intact. Unknown diagnostics never clear a prior matching negative verdict; later approval updates evidence only. Resuming requires an explicit reviewed settings operation, with a fresh automatic cutoff and no blocked-interval backlog.

For future HTTP422 responses, only fixed allowlisted validation field names are retained in error categories. Raw provider error prose, recipient numbers and message bodies remain private and unlogged. Error reads retain the128KB cap; there is no POST retry. These hints cannot reconstruct historical provider responses or prove the cause of earlier rejections.

Before reporting resolution, correlate the current LIVE source/instance, fresh sender diagnostic, signed configuration and credit access. A sender prerequisite failure is an external operator/provider action, not permission to forge approval or modify credentials. Do not claim accepted delivery, handset receipt or charges without actual evidence.
