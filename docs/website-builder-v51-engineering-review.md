# Website Builder V5.1 engineering integration

22 October 2026. Original PR #36 head: `235042870d73f2d793cd16e7e12b8ed7ed539a23`; production base: `7dd053f64b8a70643302aa57db59f2fa3ba1f594`.

## Corrections and contracts

- Preserve both original Claude commits and the existing creator UI. No schema migration, new environment requirement, pricing formula, reserve, payment, supplier, Wallet, withdrawal or referral calculation is introduced.
- `PUT /api/websites/:id/bundles` retains `{expectedVersion,products:[{productId,retailMinor,enabled}]}`. All rows, version and audit commit in one transaction. A stale version yields 409; a rejected row rolls back the batch. Ownership, archived-site rejection and the Data-template requirement are checked on that transaction's connection. The previous nested pool checkout could time out with five simultaneous requests against the five-client pool; this was reproduced against unchanged main-equivalent code in disposable PostgreSQL. The corrected native race has one successful save and four safe version conflicts, with no timeout or leaked client. Inactive products are explicitly rejected.
- Owner GET `eligible` means the product is active, global reseller policy is enabled, wholesale is enabled, owner price/activation is valid and the configured reserve/minimum is met. It does **not** prove publication, the published Data template, Paystack configuration, current supplier availability or a successful checkout preflight. Success wording distinguishes catalogue rules from actual customer purchasing. Changing only prices preserves activation; disabling affects only chosen networks; unchanged rows are omitted. Paid order snapshots remain unchanged.
- Pricing saves use refreshed server eligibility counts. A successful PUT followed by a failed refresh reports that the settings were saved, without falsely promising that nothing changed. An unconfirmed transport result requests a reload before retry. Session/site changes invalidate old catalogue and save feedback. The error transport carries HTTP status without changing endpoint bodies.
- The authenticated editor reuses its existing owner bundles response, projects only public-shaped product fields through `websitePreviewCatalog`, and sends that projection through the existing origin/window/channel/site/template-validated frame message. No token, wholesale data or policy is passed into the frame. Draft preview never calls the public storefront endpoint. Empty/unavailable draft catalogues have explicit setup guidance. All preview payment, tracking, recovery and analytics guards remain in place. No public draft endpoint was added.
- `WebsiteStore.publishSite` checks the authoritative saved public content while holding the existing owner lock. The editor and server use `websiteContactIssue` from the shared readiness module. Classic Kitchen, Night Kitchen, Boutique and Classic Shop require a structurally usable WhatsApp number, using the existing public wa.me normalization. Other non-Data designs require a supported contact; Data does not require WhatsApp. Incomplete drafts can still be saved. A rejected publish does not change the live snapshot. Existing ownership/version/example-review/media validation remains authoritative.
- **Legacy rule:** existing public pages are never read-time unpublished or rewritten. A currently published site may republish unchanged public content (including settings-only cosmetic changes) without a newly required contact. The exemption requires the same template and a trusted existing published snapshot; a pre-snapshot legacy row is eligible only if its saved timestamp still equals its publication timestamp. Material content changes, a design change, first publication, or republication after unpublishing must meet the contact rule. A valid old contact cannot be removed by a changed publication. Client request bodies cannot supply an exemption.
- PostgreSQL JSONB reorders keys. Draft/live and legacy comparisons now ignore object-key ordering while retaining array order, preventing false unpublished-change and legacy-contact errors. A native JSONB fixture independently exposed and verifies this correction.
- Explicit cross-industry template switching still uses the established confirmed migration/checkpoint flow. Same-family content is retained; different-family content resets only as described in the existing migration summary and can be restored from the checkpoint. V5.1 supplies appropriate Signal starter wording and Buy Data labels. IDs, slugs, owner identity, media library and live snapshot do not change during draft switching. No background content migration runs.
- Deletion is still guarded by server-authoritative unresolved orders and account Store Earnings. The support message uses the server website name/address, blocker amounts and current withdrawal policy, is URL-encoded, and includes no tokens, private customer numbers, internal IDs or ledger details. It only composes a message; it does not send one, settle funds, waive a minimum, move money or bypass archival guards.
- The gallery count also excludes Start Blank from the displayed count, fixing a possible “16 of 15 designs” after expanding the gallery.

## Pool-test diagnosis

The reported six cancellations were not reproduced on this Windows/Node 24 runtime: both the original candidate and main-equivalent source passed all 13 lifecycle checks before correction. Source inspection identifies the socket-free fixture's missing real-client lifetime: `pg-pool` unrefs an exhausted queue's timeout, while a real held PostgreSQL client keeps a referenced socket alive. The old fixture's `ref`/`unref` were no-ops and it supplied no socket handle. The fixture now models that connected lifetime with a timer cleared on disconnect and real ref/unref behavior. The exhaustion test also has a bounded timeout. No assertions were removed, no cancellation is counted as a pass, and production pool/shutdown code and the maximum of five are unchanged. Exact reproduction of the original runner remains unavailable; the explanation concerns test liveness, separate from the independently reproduced pricing nested-checkout defect.

## Separate financial assignment — not implemented

Exceptional settlement of below-minimum reseller Store Earnings during website closure needs a restricted Admin workflow with explicit closure eligibility, current balance/reservation checks, actual external payout evidence, immutable ledger entries, idempotency and concurrency protection, authorization and an audit history. It is not a general withdrawal-minimum bypass. Preserve access to funds/history and existing deletion blockers until an evidenced settlement is complete. Never silently write off a remainder, transfer it to Wallet, lower the global minimum or mark it paid without provider/operator evidence.
