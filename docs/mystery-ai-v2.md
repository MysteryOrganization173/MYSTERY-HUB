# Mystery AI V2: reliability, intent and verified guidance

## Audit before implementation — November 4, 2026

Fresh remote main is `b8f746cb29aa0073583d0e6a1fab6db2451f3e9f`, including Claude's V7.5 PR #86. The supplied d55caf4 baseline is older. Builder/editor/template/business components are read-only references for this task.

The full path is MysteryAiAssistant → mysteryAiService → POST /api/mystery-ai/chat → request validation → bounded catalogue/context → Gemini (at most two existing models) → public response/guide → frontend rendering/navigation. Existing AiRequestGate handles duplicate sends, cancellation, reset and account changes. History is the latest eight prior turns; current question is appended once. There is no account/tool integration or transcript persistence.

Confirmed defects:
- inferQuickAction considers generated answer text and broad words such as credit/network/template/order. A company explanation, thanks, generic credit question or multi-service comparison can get an unrelated action. Airtime actions do not select the existing Airtime mode.
- Builder scripts match incidental phone/logo/bundle words and name old tabs. Current editor uses Edit/Design/Settings/Preview/More, publication checks and Update Live; deletion is managed outside the old Danger Zone. Chat also discards the available safe editor context by sending undefined.
- Server TIMEOUT becomes a frontend exception before a known local guide can run. Timeout text blames the customer's connection despite server-side evidence. Provider CANCELLED can retry another model. Retry-After is displayed in text but not enforced by the Retry control.
- Shared fallback matches generic water/website/price words and cannot use prior user context. It conflates seller earnings and referral questions and repeats a platform directory for short conversational replies.
- Existing health counts provider attempts/successes but not guide/fallback/request outcomes, making mitigation visibility incomplete. The delivery guard also mistakes the product name Instant Bundles for a delivery guarantee.

Evidence: new deterministic regression tests on unchanged application code: 19 tests, 1 passed / 18 failed. Existing full baseline: 3,030 passed / 40 skipped / zero failures. A bounded Render log sample contained 9 failed provider attempts (8 TIMEOUT, 1 PROVIDER_UNAVAILABLE), not nine distinct customer failures; no success denominator/account quota conclusion is available. One non-sensitive baseline company question returned HTTP200 guide fallback, TIMEOUT, backend9503ms / HTTP9.838s. It did not demonstrate a working remote generation.

The existing 9500ms backend overall budget, 8000ms attempt cap, 1000ms catalogue cap and 12000ms client budget are already bounded and ordered. No blind timeout increase, new provider/model, infrastructure change or financial integration is justified.

## Focused plan

Use one lightweight user-intent/context policy for navigation and grounded guides, with no second AI call and no inference from generated wording. Resolve short references from recent customer turns and relevant page/editor hints; prefer no action if ambiguous. Precisely scoped editor instructions and simple conversational acknowledgments can be immediate; broader reasoning remains the existing remote assistant. Known operational help remains available during outages and is labelled Help guide.

Keep deadlines/model costs/rate and concurrency bounds. Share safe failure categories, preserve cooldown metadata, enforce manual Retry waiting, and stop alternate-model retry on cancellation/configuration/safety. Add only bounded process-local outcome/latency counters to existing Admin-only health. No messages, identities, credentials or raw provider bodies in diagnostics.

Ground Builder help in merged V7.5: save versus published snapshot; Publish/Update Live checks; Edit selected catalogue items; Design/Colors/Images; managed Bundles/pricing versus ordinary catalogue/WhatsApp ordering; My Business and deletion safeguards. Free plan limits come from current shared configuration, not invented plan entitlements. Runtime service availability, final prices, orders, balances and refunds remain outside chat's authority.

Verification and release evidence will be recorded with the PR: focused failure/navigation/context matrices; original protections; full regression; TypeScript/build/diff checks; real Chromium at 360/390/430px with synthetic APIs; adversarial self-review plus independent review; current-main integration, CI and actual Render revisions. No live customer transactions, records, publication, supplier submissions or notification changes are authorized by this task. Rollback is an ordinary application revert/redeploy; no migration is needed.

## Implementation and evidence rules

- Navigation accepts the current customer message, the latest eight prior turns and safe page/editor hints. It never accepts generated answer text. Exact destinations and first-person/imperative workflows may get one supported action; thanks, explanations about other people, negation, ambiguous comparisons and unsupported targets do not. Follow-ups resolve the most recent substantive customer topic. Service names qualifying a delayed/paid/refund/tracking order are part of that order problem. Airtime/Instant actions select the existing data-page mode only after a click.
- Only exact acknowledgments and narrowly scoped editor tasks are immediate guides. Broader questions keep the existing model route. Shared fallback uses the same current public facts, labels Help guide, separates Store Earnings/Wallet/Mystery Earn and supplies no private status, live supplier availability or invented prices. General phone, water-cycle, credit or unrelated publishing questions are not platform scripts.
- Client fetch and response-body parsing share one abort/race deadline; parent cancellation always rejects. Known help survives a server timeout/configuration outage. Explicit rate limits, validation, cancellation and safety failures stay explicit. Manual Retry respects bounded Retry-After metadata; no auto-retry was introduced. Existing account/reset/close request identity protections remain.
- Backend models, 512-token cap, one SDK transport attempt, two-model bound, concurrency four, 12 requests/socket-address/minute, 60-second quota/configuration cooldown, and 9.5-second overall budget remain. CANCELLED does not try another model. The delivery guard recognizes Instant Bundles as a product name. A narrow guard rejects direct opening claims of unsupported tool execution and allows clearly framed customer drafts. These guards are not general fact-checkers.
- System context uses only an injected catalogue snapshot, never default seed prices as live evidence. No snapshot means unknown, not a declared outage. Builder instructions reference merged V7.5 controls, publish checks and Update Live. Directory status is separate from runtime availability; planned utilities and unavailable Plus/Pro plans are not presented as purchasable.
- GET /api/mystery-ai/health stays Admin-only/no-store. failureCounts counts failed provider attempts; requestOutcomes distinguishes generated/instantGuide/fallbackGuide/unavailable/disconnected admitted server requests. Latency summarizes completed admitted requests, including guide responses. Validation/rate/concurrency rejects and frontend-only guides are outside those counters. State is process-local and resets on restart; providerAccessVerified only follows an actual model generation. No transcript, user ID, new DB writes or telemetry service was added.

## Remaining operational limits and rollback

Provider timeouts observed before release do not establish quota/configuration/network root cause. A guide response is not proof of provider recovery. Verify source=gemini independently before claiming remote generation works. Admin metrics describe only one process lifetime, not durable platform availability. Existing socket-IP rate limiting may aggregate clients behind a shared proxy; changing proxy trust requires verified production topology and is deferred. English intent rules prefer omission when unclear and do not guarantee understanding every phrasing; no extra AI request or new provider is used.

Rollback is an ordinary revert of the application PR followed by the existing Render deployment process; no schema, credentials, published website content or financial state needs reversal. PR #69, supplier/payment integrations, notification settings and Claude's Builder/editor/template components are untouched.
